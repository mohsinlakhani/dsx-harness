# Data Access: Luna realistic slice

_Status: draft for review. Approved in design discussion on 2026-09-02._

## 1. Purpose

Run the existing Data Access v2 three-arm protocol on three pre-registered tabular
files from DataSciBench, using GPT 5.6 Luna and packets generated by the current
`dsx-packet build` path.

This is a **new study identity**, not a reinterpretation of the 2026-08-27 Terra
pilot. Terra artifacts stay frozen and are not pooled with these results.

**Question.** On three frozen DataSciBench tables, with Luna and the Data Access
planning/review contract held fixed, how do generated DSX Packets compare with
on-demand SQL discovery and with both, on quality, evidence, uptake of
identifier and imbalance facts, time, and cost?

**Inheritance from DataSciBench.** Datasets only. Do not import original prompts,
TFC tests, or leaderboard scoring.

## 2. Arms and contracts

Reuse `dsx-data-access` (`prepare`, `run`, `judge`, `reveal`) and the v2
manifests, SQL tool, fairness proof, v1 oracle, and evidence protocol.

| Arm | Receives | Does not receive |
| --- | --- | --- |
| `dsx_packet` | Committed opaque `packet.json` from `dsx-packet build` | `query_data` |
| `full_data` | Read-only `query_data(sql)` over every row in `dataset` | The packet |
| `packet_and_full_data` | Both | Neither |

The packet remains opaque at runtime. The runner does not interpret modules.
Allowed arm deltas are only packet presence, dataset descriptor, and tool
availability. Luna, system prompt, task prompt, reasoning and service settings,
response schema, output-token limit, and terminal decision contract are common
commitments.

Do not add a third experiment package. Do not build an `ExperimentSpec`
compiler as a prerequisite. Do not change published Terra inputs, runs, or
reports.

## 3. How current builder features enter the study

1. **Generated packets.** Every live packet comes from `dsx-packet build` with
   the case target. Hand-authored JSON is out of scope.
2. **Default modules.** Each packet includes `dataset-profile`
   (`profile.dataset/v1`), `column-profile` (`profile.columns/v1`),
   `target-profile` (`profile.target/v1`), `data-traps` (`risk.data_traps/v1`),
   and `feature-risks` (`risk.features/v1`), in that order.
3. **No fabricated history.** Do not invent transformation manifests for
   imported DataSciBench files. Include `transformation-history` only when a
   case has a real declared manifest. For this slice that module is expected to
   be absent.
4. **Task assembly as a freeze gate.** Before a case is frozen,
   `assemble_task_packet` must succeed for a review-classifier `DsTask` that
   requires those five module types. The live payload is still the **full**
   builder `packet.json`, not a task projection. This study is packaging versus
   discovery, not routing.
5. **Build provenance.** Commit `build-record.json` next to `packet.json`. Time
   the build command and pass `PacketBuildMetrics` into `prepare`. The build
   record does not currently store elapsed time or cost; do not pretend it does.
   Local profiling has zero model-token cost unless a future builder calls a
   provider.

## 4. Case freeze

Cases are frozen **after** download and builder inspection. Hugging Face dataset
`zd21/DataSciBench` is gated; `case_id`s are assigned only after files are
readable.

### Eligibility (all must hold)

- Tabular CSV or Parquet.
- One defensible classification target in the file. Binary is preferred. If
  multi-class, the target must have at most 10 distinct non-null values.
- `dsx-packet build` succeeds on the frozen copy.
- At least one eligibility signal (defined below).
- Fits the current `prepare` path, which materializes and digests every row
  with no sampling: at most 20,000 rows and 40 columns. The 12 SQL attempts,
  1,000-row cap, and 64 KiB cap must still allow aggregation over the full
  table. Reject anything larger rather than changing materialization.
- Usable license. No images, visualization-only dumps, or tables with no target.

### Eligibility signals (at least one)

Measured on the committed builder packet, not by hand inspection:

- `feature-risks` contains at least one `likely_identifier` finding; or
- `data-traps` contains `target_class_imbalance` (builder threshold: minority /
  majority class count `< 0.20`, or a single class); or
- `dataset-profile` has at least one column with `missing_rate >= 0.05`.

### Diversity (preference, not a substitute for the bar)

Prefer complementary stresses across the three tables: identifier-heavy,
imbalanced target, and material missingness. If the licensed slice cannot supply
all three, keep the eligibility bar and record which stresses are missing.

### Shared task

All three cases use the same planning/review prompt and response contract: a
classifier for a 5% manual-review budget, structured decision, factual claims
only when cited exactly. Only `case_id`, dataset path and digest, `target_column`,
and the generated packet differ.

### Frozen case tree

Under gitignored `artifacts/data-access-luna-realistic/<case_id>/freeze/`:

- local dataset copy and SHA-256 of that file
- `case.json` (`oracle_version: v1`)
- builder bundle: `packet.json`, `build-record.json`
- `packet-build-metrics.json` from timed build
- freeze note: DataSciBench source id, license acceptance, dataset-only
  inheritance, packet digest, module IDs, which eligibility signals fired

`prepare` materializes DuckDB from that frozen copy. Source prompts and TFC
artifacts are not stored.

### Stop rule

If fewer than three tables pass, do not fill with the synthetic pilot or a
hand-authored packet. Stop and either select another licensed file or shrink
the study claim.

## 5. Execution

Scale: **three cases × three three-arm repetitions = 27** intended live outputs.

Each case is an independent Data Access v2 `prepare` → `run` root. Cases are
never mixed in one manifest.

**Per case**

1. Use the frozen packet, dataset, Luna model identifier, pricing snapshot, and
   packet-build metrics.
2. Run three repetitions with a recorded order seed. Randomize arm order within
   each repetition. Fresh model state per arm.
3. Use Data Access default limits: 16 model calls, 12 SQL attempts, 4,096
   output tokens, 10-minute arm cap, 10-second SQL timeout, 1,000 rows /
   64 KiB per result, sequential tools. Do not raise these per case.

**Model.** Commit one Luna identifier at prepare, the same way Terra was
committed as `gpt-5.6-terra`. If that identifier is not callable on the existing
OpenAI Responses path (`OPENAI_API_KEY` + `MODEL_ID`), stop before live calls.
Do not splice Cursor-chat transcripts into the ledger.

**Retries and destinations.** Append-only ledgers, exclusive run roots,
fresh-repetition retries for infrastructure exhaustion. No resume. No overwrite
of Terra or of a finished case root.

**Suite loop.** Add a thin `dsx-data-access suite` command that sequences the
existing `prepare` and `run` CLIs over the three freeze directories and writes
a pooled index of case roots. It does not introduce a second scoring language.
If one case fails, the others keep their artifacts; the pooled report marks the
failed case ineligible. `judge` and `reveal` remain per-case commands.

**Cost.** Inference cost from the committed pricing snapshot, recorded
packet-build wall time, estimated packet-build cost (zero for local builds),
and amortized packet cost at 1 / 10 / 100 reuses for the two packet-bearing
arms.

## 6. Scoring, blinding, and uptake

### Objective

Apply the existing v1 oracle and evidence protocol to every completed arm:
claim support, unsupported, contradicted, unverifiable; SQL replay; packet
pointer resolution; timing; model and SQL calls; token buckets; estimated cost;
discovery failures.

Computation replay stays `not_applicable` unless a compatible builder trace
adapter exists. Generic packet pointers remain artifact-level evidence.

The v1 oracle’s `likely_id` predicate is uniqueness rate `== 1.0` on a
non-target column. The builder’s `likely_identifier` also requires a fully
populated column (`non_null_count == row_count`). Do not change the oracle for
this study. Uptake diagnostics (below) use the committed `feature-risks`
findings.

### Uptake diagnostic (post-reveal, not a blind item)

After judgments freeze, for each completed output record:

- whether the decision excluded every `likely_identifier` column in the
  committed packet (packet-bearing arms) or every oracle `likely_id` true
  column (`full_data`);
- whether imbalance or the `target_class_imbalance` trap is acknowledged when
  that finding is present;
- for packet-bearing arms, whether cited packet pointers resolve into
  `column-profile`, `feature-risks`, or `data-traps`.

This diagnostic must not appear in the public blind bundle.

### Blind qualitative review

Full Data Access mask / freeze / reveal on all 27 completed outputs. Public
bundle contains decisions and claim statements only. Arm identity, packet
payload, SQL, evidence locators, usage, cost, automatic scores, and uptake
diagnostics stay private until freeze.

The judge scores decision quality, evidence use, and limitations quality (1–5)
and may guess the arm. One judge. Case identity may be obvious from table
content; arm identity must not be. Use **one frozen blind bundle per case**,
because `judge` already takes a single run root. Do not encode arm in public IDs.

### Pooling and exclusions

Primary analysis is within-case, within-repetition contrasts:

- `dsx_packet - full_data`
- `packet_and_full_data - dsx_packet`
- `packet_and_full_data - full_data`

Then report the same contrasts as three-case ranges or sign counts. No
t-tests. Incomplete arms drop that repetition from efficacy and still appear in
the operational ledger. Do not pool Terra scores with this study.

## 7. Allowed claim

On these three frozen tables, under these limits, with this generated packet
and this Luna identifier: how packet delivery, SQL discovery, and both compared
on quality, evidence, uptake of identifier and imbalance facts, time, and cost.

**Not claimed:** general DSX superiority, DataSciBench leaderboard lift, or that
the builder matches a hand-authored packet.

### Pre-registered stop/go

- If packet-only matches combined quality at lower cost on at least two cases,
  packaging is earning its keep on real tables.
- If SQL-only dominates quality and the packet is unused or wrong, the next
  experiment is the builder (or packet content), not another three-arm idea.
- If all arms collapse, the review-classifier recast was a bad fit for those
  files.

## 8. Documentation and code surface

Add, without altering Terra results:

- this spec;
- a protocol note under `docs/experiments/` for the realistic slice, linked
  from `docs/experiments/README.md` as a Data Access follow-on study, not a
  third harness;
- results narrative after reveal;
- a thin `dsx-data-access suite` command, a freeze/eligibility helper, and the
  post-reveal uptake diagnostic, with tests.

Datasets, packets, and run ledgers stay under `artifacts/` and remain gitignored.

## 9. Out of scope

- DataSciBench prompts, TFC functions, success/completion rates
- Hand-authored or edited packets
- Invented transformation manifests
- Task-scoped live packets or a packet router
- New experiment package or `ExperimentSpec` compiler
- Changing Context Lift or published Data Access Terra artifacts
- Inferential statistics
- Calling Luna outside the OpenAI Responses client used by `dsx-data-access`

## 10. Open operator inputs (not design gaps)

These are recorded at freeze/prepare, not left as protocol TBDs:

- Hugging Face access and the three source file ids
- Exact Luna model identifier string
- Pricing snapshot for that identifier
- Order seeds per case
- Judge identity for the 27-output blind pass
